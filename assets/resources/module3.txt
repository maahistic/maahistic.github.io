Overview of Relational Database Foundations
The lecture focused on foundational concepts of relational databases, covering the necessity of relational data storage, key database structures such as tables, rows, columns, primary keys, foreign keys, and the importance of database schema design. It also introduced the connection between databases and data analysis or machine learning workflows, and briefly touched upon types of machine learning.

Relational Databases and Problems with Single Table Storage
Issue with storing all data in a single big table: Storing all related info (orders, customers, restaurants, dishes) in one large table or spreadsheet leads to several problems like data redundancy, difficulty in updating information (e.g., changing phone numbers or addresses), and accidental deletions. For example, updating a restaurant phone number in multiple rows becomes cumbersome and error-prone.
Need for multiple tables: Splitting data into several logical tables (e.g., Customers, Restaurants, Orders) solves many problems:
Easier updating and deletion.
Reduced redundancy.
Simplified data management.
Tables consist of rows and columns: Rows represent records (e.g., each order or customer), and columns represent attributes or features (e.g., customer ID, order amount).
Primary Keys, Foreign Keys, and Relations
Primary Key (PK): A unique identifier for each record in a table (e.g., customer_id uniquely identifies a customer). This is similar to unique personal identifiers like Aadhaar or passport numbers.
Foreign Key (FK): A key used in one table to reference a primary key in another table, creating a relationship between tables (e.g., customer_id in Orders table referencing customer_id in Customers table).
Relational databases: Structured collections of tables where relationships are defined via primary keys and foreign keys, allowing complex queries and efficient data retrieval across multiple tables.
Database Schema and Design
Schema: The blueprint or design of the database, which lays out:
How many tables are needed.
The columns (attributes) in each table.
How tables are related via keys.
Proper schema design is essential for maintaining organized, scalable, and efficient databases, similar to how architectural blueprints guide the construction of a building.
Linking Database Concepts to Data Analysis and Machine Learning
Data from multiple related tables can be joined and retrieved as a single dataset (e.g., using SQL JOIN operations) to be used as input (data frames) for machine learning models.
Example: Using customer, order, and restaurant tables to build a dataset for predicting what dish a customer might order next.
Machine learning models on relational data involve features (attributes/columns) and records (rows), and such models may be of two major types:
Classification: Predicting categorical outcomes (e.g., predicting which dish a customer will order).
Regression: Predicting continuous numeric outcomes (e.g., sales amount, watch time).
Types of Machine Learning
Supervised Learning: Learning from labeled data under the supervision of a teacher or guide (e.g., predicting a label or category based on input features).
Unsupervised Learning: Learning patterns from unlabeled data (e.g., clustering users based on behavior without predefined labels).
Reinforcement Learning: Learning by trial and error, with feedback from the environment (learning from actions and rewards or penalties).
Practical Insights and Additional Points
SQL (Structured Query Language) is the standard language used to query and manage relational databases.
Different SQL databases exist (MySQL, PostgreSQL, SQLite, etc.), but SQL itself remains consistent.
Real-world examples like food delivery apps (Swiggy, Zomato), Netflix, Uber/Ola, and library systems illustrate the practical utility of relational databases.
Efficient data storage and retrieval in relational databases make building machine learning models simpler and more effective.
Updates, deletions, and insertions (CRUD operations) become easier and less error-prone through relational structuring.
Summary of Key Terms
Term	Description

Primary Key	Unique identifier for each row in a table (e.g., customer_id).
Foreign Key	A column in one table that refers to a primary key in another.
Schema	Blueprint/design of database defining tables and relationships.
Structured Data	Data held in tables with rows and columns.
SQL	Structured Query Language for handling data in relational databases.
CRUD	Operations on databases: Create, Read, Update, Delete.

Understanding Data Connection:
Queries on relational databases retrieve data by connecting related tables via keys. For example, counting students enrolled in a specific course involves querying the attendance or student-course mapping table.

Limitations of Excel:
While Excel allows simple data filtering and counting, it has row limitations (~1 to 1.5 million). Big companies dealing with millions of daily transactions (e.g., Walmart, OTT platforms) require databases and SQL for efficient querying.

Introduction to SQL
What is SQL?
SQL is a structured query language used to ask questions ("queries") to databases. It is essential for extracting, filtering, and aggregating data stored in relational tables.

Basic SQL Query Structure:

SELECT specifies columns to retrieve.
FROM specifies the table to query.
WHERE applies filtering conditions on rows.
Example:

SELECT name, rating 
FROM restaurants 
WHERE rating > 4.5;
Selecting All Columns:
Using SELECT * FROM table_name fetches all columns from the table.

Filtering and Conditional Clauses
Numeric Filters:
Operators such as =, !=, <, >, <=, >= allow numeric comparisons in WHERE clauses.

Non-numeric Filters:

Use LIKE for pattern matching (e.g., names starting with 'M', containing 'masala').
Use IN to filter based on a set of values (e.g., cities in a list).
Use BETWEEN for range-based filtering on numeric data.
Logical Operators:

AND requires all conditions to be true.
OR requires at least one condition to be true.
NOT negates a condition.
Examples:

SELECT name FROM restaurants WHERE city = 'Delhi' AND rating > 4.2;
SELECT name FROM restaurants WHERE city IN ('Delhi', 'Mumbai');
SELECT name FROM restaurants WHERE name LIKE '%biryani%';
Important SQL Clauses and Keywords
DISTINCT:
Used to remove duplicates and fetch unique values from one or more columns.

Example:

SELECT DISTINCT city FROM restaurants;
ORDER BY:
Sorts the result by specified columns in ascending (default) or descending order.

Example:

SELECT name, rating FROM restaurants ORDER BY rating DESC LIMIT 5;
Here, LIMIT restricts the number of rows returned.

Role of Agentic Platforms and AI in Querying

New AI tools like Codex and cloud-based agents can transform natural language questions into SQL or Python code, simplifying querying for non-experts.

Understanding SQL allows users to verify and correct these AI-generated queries.
Knowledge of SQL is essential to interpret, debug, and optimize database queries.
How Agents Understand Queries:
They perform schema discovery and employ similarity matching between user queries and table/column names using vector representations.

Introduction to SQL Joins
Joins combine data from two or more tables based on related columns.
Common real-life examples: customers and their orders, students and courses, users and shows watched.
Joins help answer questions like:
Which customers have placed orders?
Which shows have been watched or never watched?
Which students know Python or SQL?
Types of Joins Explained
Inner Join

Returns records with matching keys in both tables.
Acts like an intersection of two tables.
Example: Retrieve employees with valid department IDs by matching employee and department tables on department ID.
Left Join (Left Outer Join)

Returns all records from the left table and matching records from the right table.
Unmatched right table results return NULL.
Used to get all employees along with their departments, including those not assigned any department.
Right Join (Right Outer Join)

Returns all records from the right table and matching records from the left.
Very rarely used because reversing table order and using a left join can achieve the same result.
Conceptually symmetrical to left join but usually redundant.
Full Outer Join

Returns all records when there is a match in either left or right table.
Includes unmatched rows from both sides.
Used rarely but helpful for complete data audits.
Cross Join

Produces a Cartesian product of rows from both tables.
Example: All t-shirt types combined with all sizes.
Typically results in a large number of rows and used in specific scenarios.
Self Join

Joins a table with itself.
Useful to represent hierarchical data like employees and their managers.
Example: Mapping employee IDs to their manager IDs within the same employee table.
Practical SQL Join Syntax
Basic structure:
SELECT [columns]
FROM left_table AS alias1
[INNER | LEFT | RIGHT | FULL OUTER | CROSS] JOIN right_table AS alias2
ON alias1.key = alias2.key;
Aliases (AS e, AS d) simplify queries, especially with many columns.
Example for inner join between employees and departments:
SELECT e.name, d.name
FROM employees AS e
INNER JOIN departments AS d
ON e.department_id = d.id;

Important to normalize data into multiple tables to avoid redundancy.
Joins reconstruct the full dataset for analysis or reporting.
Example with Netflix data:
user_details, show_details, and watch_history tables.

Emphasis on problem-solving: focus on logic and approach, not just memorizing syntax.
Use iterative joins (e.g., left join watch history with show details, filter, then join with user details).

Primary Key: Unique identifier within a table (e.g., student_id in students table)

Double quotes denote column names in SQL

5. Filtering Data with WHERE Clause
The WHERE clause extracts specific rows matching conditions:

Comparison Operators

= (equals)
!= or <> (not equals)
>, < (greater than, less than)
>=, <= (greater than or equal, less than or equal)
Multiple Conditions

IN: Select from a list of values
SELECT name FROM students WHERE city IN ('Delhi', 'Mumbai', 'Pune');
NOT IN: Exclude values from a list
SELECT name FROM students WHERE city NOT IN ('Bangalore', 'Kolkata');
Range Filtering

BETWEEN: Select values within a range
SELECT name FROM students WHERE age BETWEEN 19 AND 21;
Text Matching with LIKE

% matches any number of characters
_ matches exactly one character
SELECT name FROM students WHERE name LIKE 'A%';        -- starts with A
SELECT name FROM students WHERE name LIKE '%a';        -- ends with 'a'
SELECT name FROM students WHERE name LIKE '%sh%';      -- contains 'sh'
Null Handling

SELECT name FROM students WHERE scholarship IS NULL;
Combining Conditions

AND has higher precedence than OR
Use parentheses to control execution order:
SELECT name FROM students WHERE (city = 'Delhi' OR city = 'Pune') AND year = 1;

LIMIT: Restrict number of returned rows
OFFSET: Skip the first N rows before selecting

This lecture covers three major SQL concepts: Set Operations, Subqueries, and Common Table Expressions (CTEs)
Overview
This session provides foundational knowledge on advanced SQL techniques used for combining data from multiple tables, filtering data based on complex conditions, and organizing queries for better readability. The instructor emphasizes that these concepts are essential for writing industry-level SQL queries.

Set Operations
Set operations allow you to combine or compare data from multiple tables with the same structure. These operations are called "set operations" because they work like mathematical set theory using Venn diagrams.

Key Requirements for Set Operations:

Both tables must have the same number of columns
Column names must be exactly identical
Column order must be the same
Data types should be compatible
Types of Set Operations:

UNION ALL: Combines all rows from both tables, including duplicates

Example: If Table A has 200 employees and Table B has 300 employees, UNION ALL returns 500 rows
UNION: Combines all rows but removes duplicates, returning only distinct records

Example: If 100 rows are common between both tables, UNION returns 400 unique rows
INTERSECT: Returns only the common records that appear in both tables

Example: Returns only students who both play cricket AND are in the music club
EXCEPT: Returns records from the first table that do not exist in the second table

Example: Returns cricket team members who are NOT in the music club
This is equivalent to: A minus (A intersection B)
Practical Use Case: When Netflix needs to find unique users who logged in over the last 30 days, they can UNION data from each day's table, then apply DISTINCT to eliminate duplicates.

Subqueries
A subquery is a query nested inside another query, similar to the concept of "dream within a dream" in the movie Inception.

Structure:

SELECT columns 
FROM table 
WHERE condition (SELECT ... FROM ...)
Types of Subqueries:

Single Value Subqueries: The inner query returns one single value

Example: Finding all students who scored above the average score
The subquery calculates the average, and the outer query filters using that value
List-based Subqueries: The inner query returns multiple values used with the IN operator

Example: Finding students from specific cities (Delhi OR Kolkata)
Table-based Subqueries: The inner query returns an entire filtered table

Example: Creating a subset of data (like filtering for math subject only) and then querying that subset
How Subqueries Work:

Inner query executes first and produces a result
Outer query uses that result to filter or process data
Can be nested multiple levels deep (query within query within query)
Common Table Expressions (CTEs)
CTEs are an alternative way to write subqueries that improves readability and organization, especially for complex multi-step queries.

Structure:

WITH table_name AS (
    SELECT ... FROM ... WHERE ...
)
SELECT ... FROM table_name
Advantages:

Makes queries more readable and maintainable
Allows chaining multiple steps together
Easier to debug and understand the logic flow
Better for large, complex queries
Chaining in CTEs: You can create multiple CTEs in sequence, where each one builds on the previous result:

WITH filtered_data AS (
    SELECT ... FROM main_table WHERE ...
),
aggregated_data AS (
    SELECT ... FROM filtered_data WHERE ...
)
SELECT ... FROM aggregated_data
This creates a logical flow: Big Table → Filtered Table → Smaller Table → Final Query

Practical Context
These concepts are fundamental in industry-level SQL work where:

Data is often stored in daily partitions that need to be combined (UNION)
Complex analyses require multiple filtering steps (Subqueries)
Large queries need to be organized for team collaboration (CTEs)

This lecture focuses on how to design database tables and schemas in relational databases. Building on the previous session's coverage of set operations, this session explores the fundamental principles of database design, including normalization forms and relational integrity concepts that ensure efficient data storage and manipulation.

Key Topics Covered
1. Database Structure and Schema Components
A database schema consists of three main components:

Tables: Collections of data organized in rows and columns
Views: Saved SQL queries that retrieve data from multiple tables without rewriting the query each time
Stored Procedures: Pre-written SQL statements that can be executed via commands for repeated operations
2. Types of Databases
Beyond relational databases, several database types exist:

SQL/Relational Databases: Data organized in tables with defined schemas, queried using SQL
NoSQL Databases: Flexible schemas without rigid table structures
Document stores (MongoDB): Store data as JSON files
Key-value stores (Redis, DynamoDB): Store data as key-value pairs
Graph databases (Neo4j): Store relationships between entities as connected nodes
Vector Databases: Store data as numeric vectors for similarity comparisons
Graph Databases: Represent data as interconnected nodes and edges
3. Problems with Improper Data Storage
When data is stored without proper structure, several issues arise:

Multiple values in single cells: Makes aggregation and filtering difficult
Data redundancy: Same information repeated across multiple rows
Update anomalies: Changes must be made in multiple places
Insertion anomalies: Cannot add information about entities without complete records
Deletion anomalies: Removing records may lose important information
Example Problem: Storing multiple items in a single order column prevents accurate price calculations and inventory tracking.

4. Normalization Forms
Normalization is the process of organizing data into multiple tables to eliminate redundancy and improve data integrity.

First Normal Form (1NF)
Rule: Every cell must contain exactly one value (atomic values)
Action: Break down comma-separated or list values into separate rows
Benefit: Enables proper aggregation and filtering of data
Second Normal Form (2NF)
Rule: Must satisfy 1NF AND eliminate partial dependencies on composite primary keys
Action: Distribute data across multiple tables so each table has a single purpose
Key Concept: Every non-key attribute must depend on the entire primary key, not just part of it
Benefit: Reduces data redundancy and simplifies updates
Third Normal Form (3NF)
Rule: Must satisfy 2NF AND eliminate transitive dependencies
Action: Separate data into independent tables, each representing a single entity
Structure: Create distinct tables for students, orders, menu items, and the relationships between them
Benefit: Minimizes redundancy and makes CRUD operations (Create, Read, Update, Delete) straightforward
Example Progression:

Original table with redundant student and menu information
2NF: Separate into Orders, Menu, and Order_Items tables
3NF: Further separate into Students, Orders, Menu, and Order_Items tables
5. Composite Keys
When a single column cannot uniquely identify a row, multiple columns must be combined:

Definition: A primary key composed of two or more columns
Example: Order_ID + Student_ID or Order_ID + Item_Name
Purpose: Ensures unique identification of each row in the table
6. Relational Integrity Constraints
Three types of integrity rules enforce proper database design:

Entity Integrity
Every table must have a unique identifier (primary key)
No duplicate rows exist
Primary key values cannot be null
Ensures each row represents a distinct entity
Referential Integrity
Foreign key values must match existing primary key values in related tables
Cannot reference non-existent data
Maintains relationships between tables
Example: A student cannot register for an event that doesn't exist in the Events table
Domain Integrity
Each column accepts only specific data types and formats
Age column accepts only numeric values
Name column accepts only text
Prevents invalid data entry
Ensures data consistency within columns
7. Practical Application: Designing Database Schemas
When designing a database for applications like e-commerce, streaming services, or food delivery:

Identify distinct entities (customers, orders, products, suppliers)
Create separate tables for each entity
Use primary keys to uniquely identify records
Use foreign keys to maintain relationships
Apply normalization to eliminate redundancy
Ensure all three integrity constraints are satisfied
Example Tables for E-commerce:

Customers table (customer details only)
Products table (product information)
Orders table (order information)
Suppliers table (supplier details)
Order_Items table (linking orders to products)
8. Benefits of Proper Database Design
Easy Updates: Change information in one place only
Data Consistency: Synchronized information across the database
Storage Efficiency: Reduced redundancy saves space
Query Performance: Optimized table structure enables faster queries
Data Integrity: Constraints prevent invalid data
Scalability: Flexible structure accommodates growth

2. GROUP BY Statements
Purpose: Aggregate data at specified levels by grouping rows based on one or more columns.

Basic Syntax:

SELECT column1, AGGREGATE_FUNCTION(column2)
FROM table_name
GROUP BY column1;
Key Characteristics:

Reduces multiple rows into summary rows based on unique values in the GROUP BY column(s)
Can be combined with aggregate functions: COUNT, SUM, AVG, MIN, MAX
Multiple columns can be used in GROUP BY clause (e.g., GROUP BY branch, specialization)
Results in data compression: 10,000 transaction records may collapse to 100 customer-level records
Common Use Cases:

Calculating average scores by branch or course specialization
Counting customers in different categories
Finding total spending per customer
Determining maximum/minimum values by group
Example: To find the average marks of students in AI branch:

SELECT branch, AVG(marks) as average_marks
FROM students
GROUP BY branch;
3. The OVER Clause and Window Functions
Purpose: Perform aggregations while preserving all original rows (unlike GROUP BY which collapses data).

Basic Syntax:

SELECT column1, column2, 
       AGGREGATE_FUNCTION(column2) OVER (PARTITION BY column1 ORDER BY column3)
FROM table_name;
Key Components:

OVER: Indicates that the aggregation should append results to the original table as a new column
PARTITION BY: Defines the grouping criteria (equivalent to GROUP BY but without collapsing rows)
ORDER BY: Specifies the ordering for ranking functions (optional)
Advantages over GROUP BY:

Maintains all original rows in the result set
Appends aggregated information as new columns
Enables feature engineering by creating derived columns for machine learning
Example: Adding average marks by branch while keeping all student records:

SELECT name, branch, marks,
       AVG(marks) OVER (PARTITION BY branch) as batch_average
FROM students;
4. Ranking Functions
Ranking functions help identify the position of records based on specified ordering criteria.

ROW_NUMBER()
Assigns a unique sequential number to each row
Does not assign the same rank to duplicate values
Creates gaps in numbering (e.g., 1, 2, 3, 4, 5)
Syntax:

SELECT name, score,
       ROW_NUMBER() OVER (ORDER BY score DESC) as row_num
FROM students;
Use Case: When you need a unique identifier for each row regardless of value duplicates.

RANK()
Assigns the same rank to rows with identical values
Creates gaps when duplicate values exist
If two records share rank 2, the next rank jumps to 4 (skipping 3)
Syntax:

SELECT name, score,
       RANK() OVER (ORDER BY score DESC) as rank_number
FROM students;
Use Case: When ties should receive the same rank and gaps are acceptable.

DENSE_RANK()
Assigns the same rank to rows with identical values
Does not create gaps in ranking sequence
If two records share rank 2, the next rank continues as 3
Syntax:

SELECT name, score,
       DENSE_RANK() OVER (ORDER BY score DESC) as dense_rank_number
FROM students;
Use Case: Preferred when you want continuous ranking without gaps.

5. Partition By with Ranking Functions
Purpose: Apply ranking within specific groups rather than across the entire dataset.

Syntax:

SELECT name, batch, score,
       RANK() OVER (PARTITION BY batch ORDER BY score DESC) as batch_rank
FROM students;
Effect: Creates separate rankings for each batch, where top scorer in batch A gets rank 1, and top scorer in batch B also gets rank 1 within their batch.

Practical Applications:

Ranking students within each branch
Finding top customers within each region
Identifying highest-performing products in each category
6. Common Aggregate Functions Used with GROUP BY
COUNT(): Number of records in each group
SUM(): Total value across group
AVG(): Average value in group
MIN(): Minimum value in group
MAX(): Maximum value in group
VARIANCE(): Measure of data spread (statistical analysis)
STDDEV(): Standard deviation of values
7. Data Compression and Information Loss
Understanding Collapse: GROUP BY reduces data dimensionality; 10,000 transaction records become fewer customer-level records
Not a Problem: Compression is intentional and useful for aggregation purposes
Solution for Feature Engineering: Use OVER clause with PARTITION BY to maintain original rows while adding aggregated features
8. Real-World Applications in Data Science
Feature Engineering Examples:

Customer lifetime value: Total/average spending per customer
Purchase frequency: Number of transactions per customer
Category preferences: What product categories does a customer purchase
Recency indicators: When did customer last purchase
Behavioral metrics: Engagement frequency, watch time patterns
Business Intelligence Examples:

Daily reporting on streaming content consumption
Customer segmentation by spending patterns
Identifying top performers across regions/categories
Market analysis and competitive positioning
9. Key Differences Summary
Aspect	GROUP BY	OVER Clause
Output Rows	Reduced (collapsed)	Maintains all original rows
Use Case	Data aggregation & reporting	Feature engineering & analytics
Result Structure	Single row per group	Multiple columns appended
Combining with Other Data	Requires JOIN	No JOIN needed
10. Important Notes for SQL Practice
Always verify which ranking function suits your use case (ROW_NUMBER, RANK, or DENSE_RANK)
Use PARTITION BY carefully to ensure correct grouping criteria
Test queries on sample data before running on large datasets
Combine GROUP BY and OVER functions strategically based on analysis requirements
Remember: Data aggregation is fundamental to EDA and machine learning model development

Revision: Group By vs. Over Clause
Group By:

Consolidates data by aggregating records into fewer rows
Example: With 2,000 employees across three departments, GROUP BY reduces output to three rows (one per department) showing consolidated metrics like average salary
Syntax: SELECT column, AGGREGATE_FUNCTION(column) FROM table GROUP BY column
Over Clause:

Performs calculations across groups while retaining the original row structure
Appends new columns to the existing table without consolidation
If input table has 2,000 records, output table also has 2,000 records
Syntax: SELECT column, AVG(column) OVER (PARTITION BY column_name) FROM table
Used extensively in feature engineering
Understanding Correlation and Auto-Correlation
Correlation:

Measures linear association between two variables
Range: Values from -1 to 1, where 0.3 means 30% linear relationship
Example: Ice cream consumption correlates with temperature increase
Important limitation: Correlation does not imply causation
Auto-Correlation:

Occurs when data is dependent on its own past values
Critical concept in time series analysis
Example: Share price today depends on previous days' prices
Forms the foundation for lag and lead function applications
Time Series Data Concepts
Definition:

Data recorded at regular, equally-spaced intervals
Examples:
Daily rainfall measurements
Stock prices at 5-minute or daily intervals
Government statistics recorded every 10 years
Sensor data recorded at millisecond intervals
Importance:

Time series prediction involves forecasting future values based on historical patterns
Present value often depends on recent past values rather than distant historical data
Example: Tomorrow's share price is more likely influenced by recent trading patterns than prices from a year ago
Lag Function: Accessing Past Values
Purpose:

Retrieves values from previous time periods
Creates lagged features for machine learning models
Basic Syntax:

SELECT name, test_month, score, 
       LAG(score) OVER (ORDER BY test_month) AS previous_month_score
FROM monthly_data
WHERE name = 'Arav'
Key Applications:

Creating lag of 1: Previous month's value
Creating lag of 2: Two months back value
Creating lag of 3, 4, etc.: Multiple historical periods
Null values appear at the start since no prior data exists
With Partition By (Multiple Students):

SELECT name, test_month, score,
       LAG(score) OVER (PARTITION BY name ORDER BY test_month) AS previous_month_score
FROM monthly_data
Allows calculation of lagged values for each student independently
Eliminates need for multiple WHERE clauses
Practical Use Cases:

Month-over-month performance comparison
Calculating absolute change: score - LAG(score)
Percentage growth calculation: (score - LAG(score)) / LAG(score) * 100
Lead Function: Accessing Future Values
Purpose:

Retrieves values from future time periods
Complements lag for comprehensive temporal analysis
Basic Syntax:

SELECT test_month, score,
       LEAD(score) OVER (ORDER BY test_month) AS next_month_score,
       LEAD(score, 2) OVER (ORDER BY test_month) AS next_two_months_score
FROM monthly_data
Key Characteristics:

Lead of 1: Next month's value
Lead of 2, 3, etc.: Multiple future periods
Null values appear at the end since no future data exists
Inverse operation to lag
Relationship Between Lag and Lead:

Both functions provide similar information but from different perspectives
Lag shows past values; Lead shows future values
Can be used together to create comprehensive temporal windows
Combining Lag and Lead for Feature Engineering
Creating Lagged Features for Machine Learning:

Transform time series data into format suitable for ML models
Example: Share price prediction with multiple lag periods
Current value: 2,455
Previous day (Lag 1): 2,438
Two days back (Lag 2): 2,400
Combined in single row for model training
Data Transformation Example:

Original format: Daily observations over time
Transformed format: Each row contains current value plus multiple historical values
Result: Enables ML models to learn patterns from temporal relationships
Moving Averages and Smoothing Techniques
Concept:

Removes sharp variations and reveals underlying trends
Calculated by averaging values over specific windows (e.g., 3-day moving average)
Implementation:

Create lag features for multiple periods
Calculate average across the window
Eliminates noise from raw data while preserving trends
Use Cases:

Trend identification in noisy data
Reducing outlier impacts
Preparing data for time series forecasting
ROWS BETWEEN Clause: Advanced Windowing
Syntax:

SELECT score, test_month,
       AVG(score) OVER (ORDER BY test_month 
           ROWS BETWEEN 2 PRECEDING AND 2 FOLLOWING) AS moving_average
FROM monthly_data
Components:

PRECEDING: Look backward in time (past records)
FOLLOWING: Look forward in time (future records)
CURRENT ROW: Include the current observation
Note: Rarely used in practice; lag and lead functions typically sufficient for most use cases

Window Functions Overview
Definition:

Perform calculations across a specific time window while retaining individual rows
Window = time segment for analysis
Common Window Functions:

Lag: Access past values
Lead: Access future values
Aggregate functions with OVER clause: SUM, AVG, COUNT, etc.
Key Advantages:

Maintains original row structure
Enables comparison of individual values with aggregated metrics
Facilitates feature engineering for predictive models

Feature engineering for ML models

Predictive modeling inputs
Using CTEs with Window Functions
Advantages:

Improves readability for complex queries
Separates feature creation from analysis
Enables multi-step feature engineering
Structure:

WITH lagged_data AS (
    SELECT name, test_month, score,
           LAG(score) OVER (PARTITION BY name ORDER BY test_month) AS previous_score
    FROM monthly_data
)
SELECT *, 
       (score - previous_score) / previous_score * 100 AS percentage_change
FROM lagged_data
